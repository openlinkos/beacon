# 目标

Beacon 为什么而做、不做什么、目标互相冲突时怎么取舍。每一处改动都应该服务其中某个目标；做计划时写明是哪一个。

## 北极星 {#north-star}

Beacon 是 AI 时代基础设施中的一环：Agent 做运维的那一环。做它的人做这一类基础设施，是为了拿掉 AI 和 Agent 干活时碍事的东西，让它们用起来顺畅。其他环节（比如跨会话留存的记忆）是别的项目；Beacon 只守自己这一环。

落到 Beacon 上就是：**运维由 Agent 通过 Beacon 来做；人看得见、停得住，不用亲自动手。**

从两个角度衡量：

- **覆盖**：Agent 在机器上和告警上做的事，有多少经过 Beacon。目标：全部，而且没有一把密钥在 Agent 手里。
- **闭环**：严重告警里，有多少由 Agent 从被唤醒一直做到验证恢复，中间没有人插手。目标：多数。

三条底线不拿来换上面任何一项：不丢告警，不泄露凭据，没有一步不留记录。一项改动既不推进覆盖或闭环，也不守住哪条底线，就先放一放。

## 一句话 {#in-one-sentence}

Beacon 是 AI Agent 做运维时最顺手的基础设施：看得见服务是否正常，够得着每一台机器，让人和 Agent 在同一个平台上协作；一切都按 Agent 已有的方式来用。

两条检验标准：

- 一个 Agent 第一次接入，不读任何专为 Beacon 写的说明，只用 ssh、shell、HTTP 和 MCP，就能在一次真实故障中查清问题、在机器上修好，并让人看到它做了什么。
- Beacon 跑在哪里，那里 Agent 做的运维就全部经过它，没有人需要把密钥交给 Agent。

## 要解决的问题 {#the-problem}

运维工程师需要眼睛（监控和告警）、手（登录机器、执行命令、修改文件）、记录（做过什么，能查也能回放），以及和人的联系（被叫醒、汇报、让人看见）。Agent 需要的是同样四样，只是有三点不同：它熟悉的是 ssh、shell、HTTP、MCP 这些通用工具，不是各家产品自己的界面；它不记事，每次会话都从零开始；它也不会一直盯着屏幕，得有东西叫醒它。Beacon 按 Agent 已有的方式提供这四样，而不是另造一套让它去学。

## 为谁 {#who-it-is-for}

- **用 AI Agent 管理自己的机器和服务的人**（Claude Code、Codex 这一类）：从一个人带几个 Agent 管十几台机器，到一个小团队，都是自托管。
- **首先是做 Beacon 的人自己**：自己的运维先跑在上面，再给别人用。

## 产品目标：三根支柱 {#product-goals-three-pillars}

| 目标 | 怎么算达成（数字是目标值） |
| --- | --- |
| **1. 看得见**（监控）：服务对用户是否正常，哪里坏了，为什么 | 严重故障 5 分钟内送到 Agent 和人；单个检测点的抖动不打扰任何人；每次失败都带着检测点和原因；一次调用拿全证据 |
| **2. 够得着**（SSH 通道与密钥）：Agent 能到达每一台登记过的机器，并在上面干活 | ssh、scp、rsync、`ssh -L` 和 MCP 工具都能到达任何登记过的机器，包括 NAT 后面的；通道带来的额外延迟在 50 ms 以内（实测每次新建连接约 23 ms）；Agent 从不接触密码和密钥。它需要的其他凭据按授权取用：一次授权、多次使用，授权可以长期有效、可以续期，每次取用都能追溯到 Agent、它代表的人和原因 |
| **3. 连得上**（平台）：人和 Agent 共用一套身份、一条时间线 | 一个 Agent 在 SSH、REST 和 MCP 上是同一个身份，代表某个人行事，不超出这个人的角色；一台机器只登记一次，监控和 SSH 通道共用这个身份；一条时间线串起告警、会话、命令和备注；新告警能唤醒 Agent；人在飞书里能看到 Agent 做的每一件事，能回放，也能立即暂停 Agent |

## 设计目标 {#design-goals}

| 目标 | 怎么算达成 |
| --- | --- |
| **4. 贴近 Agent 的工作方式**（设计目标中排第一） | 用标准协议：SSH、Prometheus 查询、HTTP 加 JSON、MCP；不自创配置语言。MCP 工具和 Agent 自带的工具同名同义：执行命令、读文件、改文件、搜索、后台任务。结果干净、结构化，不夹带终端控制字符；长输出会截断，并说明怎么取到其余部分。错误码稳定，并说明怎么改正 |
| **5. 以透明代替审批** | 每次会话都有录像、可以回放，每条命令都有结构化记录，至少保留六个月。没有一条命令要等批准：审核运行什么，是 Agent 的事，由它自己的执行框架来做。Beacon 审批的只有凭据，按授权一次批准，从不按取用（目标 2）。Beacon 提供信息（比如哪些机器是关键机器），并给人一个暂停开关 |
| **6. 凭据只在 Beacon 里** | 密码和密钥只存在于 Beacon；连接机器用几分钟就失效的证书；令牌有作用域和有效期；密钥只从配置里写明的文件读取 |
| **7. 在 Beacon 里配置** | 目录、检测目标、检测模块和机器都存在 Beacon 的数据库里，通过 API、MCP 和命令行修改，并留下谁改了什么的历史；文件只用于导入和导出 |
| **8. 小** | 中心用一台 2 核 4 GB 的机器绰绰有余；检测程序和机器上的连接程序常驻内存都在 20 MB 以内；30 分钟装好 |
| **9. 开放** | Apache-2.0；实现这些目标所需的一切都在本仓库里；不绑定任何模型、聊天工具或云厂商 |
| **10. 能托管而不必分叉** | 只预留接缝（工作区、存储接口、协议版本、计量），让托管部署始终可行；这些都不提前实现 |
| **11. 可调的都是配置** | 每个可调的值都是配置项：开箱即有合理默认值，存在 Beacon 的数据库里，带版本、谁改的、为什么改，可以回滚；系统、库、标签、资格、申请逐级覆盖，越具体的越优先。只有四条不变量——记录与审批成立的前提——不可配置 |

## 不做什么 {#not-doing}

- **Beacon 不是 Agent，也不调用任何模型。**它唤醒 Agent；Agent 被唤醒时，`beacon-oncall` 启动你指定的 Agent 程序。推理和审核是 Agent 的事，Beacon 是它们干活的地方。
- **不审批 Agent 运行什么。**审批只针对凭据，按授权一次批准，从不按取用：由规则、审核 Agent 或人来决定，怎么组合是配置（见[管理 Agent 的密钥](../guide/secrets.md)）；审核 Agent 在 Beacon 之外，像值班 Agent 一样被 hook 唤醒。决定运行什么始终是 Agent 的事，由它自己的执行框架负责。密钥这边的总闸是封存保管库；SSH 通道的暂停开关仍是上机器的闸，加上每台机器的访问范围。
- **不做日志平台、链路追踪、APM 和自定义面板。**Agent 要看日志，就通过 SSH 通道直接读（journalctl 之类），这是它最熟悉的方式。
- **不自己做时序数据库。**存储和查询交给 VictoriaMetrics。
- **不做远程桌面，也不做部署系统。**Flux 这类工具照常用，Beacon 接收它们的变更事件。
- **不写只有某一处部署才需要的代码。**某处部署特有的东西都是配置，放在本仓库之外。

## 什么叫落地 {#what-landed-means}

以下三条同时成立，项目就算落地（1.0）：

1. **在 Beacon 运行的地方**：每条严重告警都会唤醒 Agent；多数由 Agent 处理完，其余的呼叫人；Agent 做的每一次运维操作都经过 Beacon。
2. **另一个团队**照着 README 用参考部署，30 分钟装好 Beacon，登记一个检测点、一台机器和自己已经在用的 Agent 程序（Claude Code、Codex 或别的），同样的闭环就在它自己的聊天工具里跑起来。
3. **人有一个地方可看**：从聊天里的卡片点一个链接，就能打开告警的时间线、每次会话的回放和暂停开关；人用 Beacon 自带的账号登录，不接外部登录。

## 目标冲突时 {#when-goals-pull-apart}

首先是不丢告警、不泄露凭据；其次是贴近 Agent 的工作方式；再次是全程可见；然后是保持小；最后才是功能多。
